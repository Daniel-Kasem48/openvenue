# OpenVenue ticketing integrations

Research checked 15 November 2026 against official documentation. This is a feasibility recommendation, not confirmation that OpenVenue has API credentials, commercial approval, or production access.

## Recommendation

Start with **pretix as an organizer integration**, keeping ticket payment and checkout with the ticketing provider. Add **Eventbrite** for organizers who already use it. Use **Ticketmaster Discovery** for event listings and outbound purchase links; defer Ticketmaster sales until a formal distribution partnership exists. Consider **Seats.io** only if OpenVenue deliberately wants to outsource seat inventory; it overlaps substantially with the existing seating engine.

## Phased implementation proposal

1. **Link and import.** Add provider and external event ID to OpenVenue events, import authorized event metadata, and offer a provider checkout link. Keep the 3D venue view as a visualization. An imported event or displayed seat is not a purchasable allocation. This adds useful integration without creating payments in OpenVenue.
2. **pretix organizer pilot.** Map OpenVenue seat IDs to pretix seat GUIDs for one venue/event. Import orders and cancellations into a provider-owned projection, refresh via webhooks plus periodic reconciliation, and delegate scanner validation to pretix's redemption endpoint. Keep existing local reservations separate from externally sold allocations. Start with read-only external seat availability before introducing writes.
3. **Eventbrite connector.** Reuse the proven event/order mapping approach with organizer OAuth and embedded checkout. Confirm seating and check-in permissions through a real account before committing to either feature. A browser checkout callback should prompt a server-side order verification, not grant admission by itself.
4. **Advanced inventory only when justified.** For a custom 3D purchase flow, explicitly choose one authority for each event's seat holds, prices and sold state. Evaluate pretix's supported integration path or Seats.io using a test event. Ticketmaster seat purchasing is a separate partner project, not an incremental Discovery feature.

Implementation judgment for NestJS/Postgres: store provider-scoped external IDs with unique constraints, keep credentials server-side, process notifications idempotently, and reconcile missed updates. Never confirm a local seat reservation merely because a cached external seat looked free. Let the inventory authority accept or reject the hold. Model cancellations/refunds independently from check-in state. A successful payment plus failed seat confirmation needs a defined recovery path before OpenVenue can own checkout.

## Specific limits to verify before implementation

- pretix's current developer docs already describe upcoming changes, expected for hosted installations in early December and self-hosted 2027.1. Pin the integration to the actual target deployment; do not build against fields marked NEW. [Orders API notice](https://docs.pretix.eu/dev/api/resources/orders.html)
- pretix cart creation trusts supplied prices and omits several normal shop validations. Do not treat it as a safe drop-in checkout API. [Cart API warnings](https://docs.pretix.eu/dev/api/resources/carts.html)
- Seats.io's documented webhooks are not a generic sold-seat event feed; evaluate the separate status-change API if booking reconciliation is needed. [Status changes](https://docs.seats.io/docs/api/list-status-changes/)
- API documentation establishes possibilities, not an approved commercial relationship. No credentials, sandbox calls, plan pricing, or contracts were tested. Some Eventbrite documentation requests returned HTTP 429; unverified seat/check-in capabilities remain explicitly uncommitted.
